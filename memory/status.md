## Current status (2026-08-24) — Anti-debug-self-test crash FIXED. Real root cause was `_rtl_unwind`'s `ESP=target_frame`, wrong for MSVC's `__global_unwind2` self-return trick. Game now reaches DirectX8 setup -- but `_invoke_handler`'s sentinel/step-budget dispatch model can't represent a handler whose control flow permanently merges back into ordinary game execution, so the whole SEH dispatch (and the run) now dies with a false "timed out" 2M steps later

**Context**: 2026-08-23's session shipped a real, correct, tested EBP-restoration fix for `RtlUnwind` but the crash recurred identically -- see `status_archive.md`'s "Previous status (2026-08-23, cont'd)" entry for that investigation's (ultimately mistaken) "garbage return address on the thread's outermost frame" theory. This session re-investigated fresh via live single-step tracing (temporary instrumentation added to `_invoke_handler`, removed after use -- `seh.py` diff-clean between probes) and found the real mechanism.

**Root cause, fully confirmed live, not guessed**: `_CLayer_DetectDebugger`'s real, compiled `__except_handler3` (`0x9f5eb8`) correctly evaluates its filter, then calls the real, compiled `__global_unwind2` (`0x9f2e90`) -- a thin CRT wrapper: `RtlUnwind(EstablisherFrame, /*TargetIp=*/its own return address, NULL, NULL)`, a well-known MSVC trick where RtlUnwind's "jump to TargetIp" simulates a normal function return so `__global_unwind2`'s own ordinary epilogue (`pop edi;pop esi;pop ebx;mov esp,ebp;pop ebp;ret`) can run afterward. `tew/kernel/seh.py`'s `_rtl_unwind` set `ESP = target_frame` before jumping -- but `target_frame` is the *SEH registration record's own address*, unrelated to `__global_unwind2`'s real, nested stack depth. So the epilogue popped the wrong things: `EDI`/`ESI`/`EBX` came back as the registration record's own `next`/`handler`/`scopetable` fields (live-confirmed `EBX=0`, the scopetable field), then `mov esp,ebp;pop ebp;ret` jumped ESP to `__global_unwind2`'s own real EBP (`0x7fffffd8`, itself near the stack top since we're only a few calls deep at this point in startup) and popped two more unrelated dwords -- one of them (`0x9f5eb8`, incidental leftover stack content, not a real return address) became a bogus `RET` target, landing back inside `__except_handler3` a second, self-reentrant time. That second entry does `push ebp;mov ebp,esp` → `EBP=0x7fffffdc` (exactly matching every crash dump seen since 2026-08-22), reads garbage `[EBP+8]` as its "exception record" (`0`), and null-derefs on `TEST [EAX+4],6`. This is also the full explanation for `ret=0x011f3b90`/`handler=0xFFFFFFFF` seen in every prior dump: incidental/stale stack content, never real return addresses -- the "garbage outermost-frame return address" theory from 2026-08-23 was a plausible-but-wrong read of this same symptom.

**Why Wine's cited precedent doesn't actually apply here**: the module docstring previously justified `ESP=target_frame` as "same approach Wine's x86 RtlUnwind takes." That's true for RtlUnwind itself (an ntdll.dll export Wine reimplements natively either way), but `__global_unwind2` is CRT-internal, not an OS API -- in this (debug, statically-linked) build it's genuine Microsoft machine code baked into the EXE, not something Wine can intercept or replace. Real Windows RtlUnwind resumes in the context of *whoever called it* (ESP as if it had just done an ordinary `RET 16`), not at TargetFrame's address -- TargetFrame only bounds which handlers get invoked with `EH_UNWINDING` during the chain walk.

**Fix**: `_rtl_unwind`'s `target_ip` branch now sets `cpu.regs[ESP] = (esp + 20) & 0xFFFFFFFF` (`esp` = RtlUnwind's own entry ESP, captured before args are read; `+20` = retaddr + 4 stdcall DWORD args, i.e. exactly the caller-return stack depth) instead of `target_frame`. Updated the module docstring and an existing test's assertion that had encoded the old (wrong) `ESP==target_frame` behavior (`test_rtlunwind_pops_current_frame_without_reinvoking_it`). Added `test_rtlunwind_resumes_at_callers_stack_depth_when_target_ip_is_its_own_return_address`, modeling the `__global_unwind2` self-return shape directly. `pytest -q`: 1237/1237. No change to the EBP-restoration logic (orthogonal, unaffected).

**Live-verified**: same crash reproduced identically 5 times pre-fix (confirming determinism before touching anything); post-fix, the bogus self-reentrant crash is gone. `~/.emu32/MCity/stdout.txt` now has real content for the first time: `clayer.c(311) SEH Handler!` / `clayer.c(318) Found Debugger!` (the `__except` block itself ran and printed -- "Found Debugger!" is a known, separate false-positive, see `status_archive.md`'s 2026-08-16 entry, not new) / `platform.c(325) dx8z.dll` / `mode:0, width:1024, height:768, hz:60, bpp:32, fmt:22` -- the game reaches DirectX8 display-mode setup, further than ever observed before.

**New blocker -- NOT a downstream DX8 bug, an architectural limit of the SEH dispatch model itself**: `__except_handler3`'s invocation runs the full `_STEP_LIMIT` (2,000,000 steps, `seh.py`) without ever returning -- "handler at 0x009f5eb8 timed out -- treating chain as exhausted," which then makes `dispatch_exception` treat the whole chain as exhausted and halts the *entire* emulator. Initially mischaracterized (in an earlier draft of this entry) as "likely stuck in DX8 init" -- corrected: `_invoke_handler`'s loop only exits on `cpu.halted` (a real `HLT`, a real fault, or `_STEP_LIMIT`); `_rtl_unwind`'s ESP/EIP redirect is just a register mutation, it never halts anything, so execution flows seamlessly from `__global_unwind2`'s epilogue through `__except_handler3`, `__NLG_Notify`, the real `__except` block, and onward into WinMain's ordinary continuation (DX8 setup and presumably the rest of the game) -- all still counted as the *same* `_invoke_handler(handler=0x9f5eb8, ...)` call, because none of that legitimately-continuing game code ever reaches the `SEH_RETURN_SENTINEL` `_invoke_handler` is watching for (nor should it -- once the `__except` block finishes, control is *supposed* to merge back into ordinary, unbounded WinMain execution, not return to the dispatcher). So the game isn't stuck anywhere in particular; `_invoke_handler`'s step-budget-and-sentinel model was designed assuming a handler is a short, bounded routine that returns, and that assumption is simply false once a handler's flow permanently escapes into ordinary program execution via this trick. The 2M-step cap is what stops the run, not a bug downstream. Needs a different dispatch strategy, not more tracing of DX8 code -- e.g. detect when a RtlUnwind-driven redirect is *not* landing back near the handler's own return-address region (a strong signal of "this resumed into unrelated, effectively-unbounded code") and hand control back to the outer run loop immediately, treating the exception as handled as soon as the redirect happens, rather than waiting on the sentinel/step-budget at all.
