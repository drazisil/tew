## Current status (2026-08-29, cont'd x43) — heap-exhaustion follow-up: wired a real guest-side `_CrtDumpMemoryLeaks` call into the crash path, worked around an `INT 3` in the game's own registered CRT report hook to get a clean dump, and got a real measured leak picture (43.47MB/10,943 blocks) for the first time — but the single 42MB block responsible for 96% of it is still unattributed. **This session's task**: re-enable the report hook and find out why it traps `INT 3`, since that may be exposing a bug in tew's own emulation rather than real CRT behavior.

**Built** (already in the working tree at the start of x43, not yet committed): `tew/kernel/exception_diagnostics.py`'s `diagnose_fault` now optionally takes `memory`/`state` and, when given them, calls the guest's real `_CrtDumpMemoryLeaks` (`0x009F81B0`, confirmed via Ghidra decompile — statically linked debug CRT, genuinely present, not a stub) via a nested `_invoke_emulated_proc` right before finalizing an unhandled fault. `run_exe.py` now passes `memory=mem, state=crt_state` at its `diagnose_fault` call site. `patch_internals.py`'s `_crt_dbg_report` handler (already the thing that logs every `_CRT_WARN` report, including each per-block leak line `_CrtDumpMemoryLeaks` produces) had its format-string substitution rewritten to go through the shared `_sprintf_format` engine (same one `sprintf`/`printf` use) instead of a bespoke single-`%s`/`%d` substitution — real leak-dump lines use `%hs`/`%08X`/`%u`/`%ld`, none of which the old code handled, so every line printed literally with no data before this fix.

**The `INT 3` problem**: the game's own registered `_CRT_REPORT_HOOK` (`crtReportHookCallback`, `0x006881a0` — the same function `patch_internals.py`'s comments already named as what drives `memleaksCRT.txt`) ends in a bare `INT 3` whenever it isn't actively mid a single leak-report burst (its own static `bIsLeakReport`-style flag). Calling the dump from tew's crash path re-enters/trips this. **Worked around, not fixed**: `_dump_crt_memory_leaks` temporarily zeros `_CRT_REPORT_HOOK_PTR` (`0x020ee23c`) for the duration of the call so the guest hook never fires at all — tew's own unconditional log line inside `_crt_dbg_report` doesn't need it. The workaround's own comment assumed this was real, expected MSVC debug-CRT-hook behavior outside a leak-report burst, not a guest bug — **that assumption is exactly what this session should test, not accept**: this may well be tew's own emulation of the report-hook/leak-report state machine diverging from real Windows (e.g. some guest-side flag, or the nested-call sequencing `_invoke_emulated_proc` uses, not matching what the guest expects around a diagnostic call made mid-fault rather than at a clean exit), not a genuine CRT quirk.

**Confirmed live, with the workaround in place**: a complete leak dump reached "Object dump complete." cleanly — **10,943 leaked blocks, 45,578,803 bytes (43.47MB) of the 64MB heap**, a measured fact for the first time, not an inference. One single block, **44,040,192 bytes (42MB), allocation #522, went through a plain `malloc()`** (not the debug-instrumented 4-arg `operator new` every tracked `new` in this binary uses) — no file/line attribution at all, 96% of all leaked bytes in one allocation. Plausibly a legitimate, still-alive, by-design allocation (the process never reaches a natural exit) rather than a bug — possibly `_MEM_init`'s single 64MB engine-arena `malloc` (see `memory/heap_and_message_pools.md` §1), though the size doesn't match that call's hardcoded `0x4000000` constant exactly, so not confirmed. The clearer bug signal: **`dbcode.c(4024)`, 10,426 separate 16-byte allocations, never freed** (~167KB total but 95%+ of leaked block *count*) — not yet decompiled, suspected tied to `DBServiceRequestQ` per-request ticket bookkeeping. Also smaller leaks at `DBQuery.c(557/758/1002)` and `DBApt.c(600/1003)`, matching the DAO `DBParamQuery`/`DBRecordset` COM-lifecycle leak theory from prior sessions.

**Also added this session**: caller-address (return-address) logging to every allocation-type handler — `malloc`/`_malloc_crt`/`calloc`/`realloc`/`operator new` (`msvcrt_handlers.py`) and `HeapAlloc` (`kernel32_memory.py`) — hoping to correlate the 42MB block back to its call site by address/size after the fact. **Did not succeed at identifying the block** even with the logging in place — noted here since no prior write-up captured that attempt or its outcome. A raw caller-address log has no way to map back to the CRT's own internal allocation ordinal (`#522`); needs a better correlation approach (e.g. a matching allocation-sequence counter) rather than repeating the same one.
