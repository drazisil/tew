## Current status (2026-08-30, cont'd x44) — Fixed a real, unrelated D3D8/Vulkan bug that was blocking every live run past ~14s; with that cleared, exercised the `crtReportHookCallback` `INT 3` question directly and traced the actual leak-report-write failure down to an exact point inside the debug CRT's first-ever-exercised private-heap allocation path, not yet root-caused further.

**The Vulkan fix (the big one)**: `_platform_vulkan_extensions()` (`tew/api/d3d8/idirect3d8.py`) unconditionally enabled *both* `VK_KHR_xlib_surface` and `VK_KHR_wayland_surface` on the `VkInstance` whenever `WAYLAND_DISPLAY` was set (i.e. always, in a real Wayland session), even though the surface only ever gets created via one of them. Confirmed via a stock `vkcube` run (same driver, same WSI path, clean 5 frames) that this was never an NVIDIA driver bug — enabling both extensions gave the Vulkan loader's `vkGetPhysicalDeviceSurfaceCapabilitiesKHR` terminator an internal Xlib-surface-recreation fallback path for a real, correctly-created *Wayland* surface, which called `XGetXCBConnection()` on a `Display*` that was never created (confirmed via Ghidra: that function is a bare double-pointer dereference, no null check) — an immediate `SIGSEGV`. Fixed to enable only the extension matching `SDL_GetCurrentVideoDriver()`'s real, live answer. **This unblocks every future live-run investigation** — nothing about window/D3D8-device creation had worked reliably before this.

**The `INT 3` question, now actually answered**: SEH dispatch is not broken. It genuinely walks real frames (same handler chain as a separate, real access-violation fault earlier in the same run) and correctly finds nothing that handles `STATUS_BREAKPOINT` at `crtReportHookCallback`'s `swi(3)` fallback (`0x006881a0`) in this diagnostic-dump context — because `bIsLeakReport` never gets set to 1. The very first `_CrtDbgReport("Detected memory leaks!\n")` call correctly enters the "leaks" branch and calls `AppendToCRTLeaksFile` for the first banner line (real `fopen`/`fputs`/`fclose` chain, confirmed via a real `CreateFile` succeeding), but that call **never returns**. Bisected step by step with 11 `cpu_add_logpoint` probes (full trace preserved as commented-out probes in `run_exe.py`, right after the DAO/Jet probe block) down to an exact point: execution reaches `__heap_alloc_base`'s own `CALL HeapAlloc` instruction (`0xa05e43`) with a completely normal, previously-successful heap handle (`h_heap=0x9001`), `dw_flags=0`, `size=4144` — and neither `_heap_alloc`'s success log nor either of its two error branches (invalid heap / unsupported flags) ever fires. Within ~1ms, unrelated code (`_CrtMemDumpAllObjectsSince`'s own "Dumping objects ->") is executing instead, itself immediately hitting the same `swi(3)` fallback (since `bIsLeakReport` is still 0) — that's the `INT 3` that's been ending every run.

**Why this specific call**: it's the first-ever exercise of the debug CRT's *private* heap allocation path (`__getbuf`'s lazy stdio-buffer allocation, only triggered by a stream's first-ever write) — every other `_fputs` call all session already had a buffer from an earlier write to the same stream, so `_malloc_dbg`/`__heap_alloc_base` were never reached from `_fputs` before tonight. `___sbh_alloc_block` (the small-block-heap fast path) is correctly skipped for our 4096-byte request (above threshold, confirmed live). **Not resolved further this session** — logpoints alone can't distinguish "the handler ran but didn't log" from "the handler never dispatched at all"; needs native-level (gdb on the Zig `cpu.run()` call) or Python-level tracing across the `HeapAlloc` dispatch boundary itself. Full narrative, including two environment detours (a wedged-compositor hang and the pre-fix Vulkan segfault) hit along the way tonight: `status_archive.md`, "Previous status (2026-08-29/30, cont'd x43)".

**Also fixed along the way** (real, but confirmed inert for this exact call chain — `AppendToCRTLeaksFile` calls `_fopen`/`_fputs`/`_fclose` via direct internal addresses, never through the `msvcrt.dll` IAT `register_handler` patches these fixes target): `_fopen`'s handler always used `CREATE_ALWAYS` disposition regardless of mode, silently truncating any `fopen(path, "a")` append-mode open instead of `OPEN_ALWAYS`-plus-seek-to-EOF — fixed (`msvcrt_handlers.py`). Registered the missing underscore-prefixed `_fputs`/`_fclose` handlers (previously only the non-underscore names existed, mirroring `fopen`/`_fopen`'s existing pair) — still worth having for any code path that genuinely calls through the public API names via the IAT.
