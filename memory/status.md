## Current status (2026-08-24, cont'd) — Anti-debug-self-test crash FULLY resolved, including the SEH-dispatch-nesting blocker. Game reaches its real main window and runs 40+ real seconds of game logic (DAO, mcity.c) before hitting a genuine, unrelated downstream ASSERT. Also fixed: SDL2 never shut down cleanly when a run was SIGTERM'd (e.g. by `timeout`), orphaning windows/GL contexts all night

**Context**: earlier this session, `_rtl_unwind`'s `ESP=target_frame` bug (MSVC's `__global_unwind2` self-return trick) was found and fixed -- see `status_archive.md`'s "Previous status (2026-08-24)" entry for that root cause. Fixing it exposed a second, previously-unreachable blocker: `_invoke_handler`'s sentinel/step-budget dispatch model has no way to represent a handler whose control flow permanently merges into ordinary, unbounded game execution (the real `__except` block, entered via a plain compiler-emitted JMP, not a second RtlUnwind call) -- it just holds the CPU hostage for the full 2,000,000-step `_STEP_LIMIT`, which then forces the whole emulator to halt even though nothing is actually stuck.

**Fix, in `tew/kernel/seh.py`'s `_invoke_handler`**: proactively raise `SehHandlerEscaped` (the same "clean escape" path already used for the post-hoc case) once `EIP` has moved more than `_ESCAPE_EIP_DISTANCE` (2MB) away from `handler_addr` itself, instead of only detecting an escape after `cpu.halted` becomes true for some other reason. `_rtl_unwind` sets a new `cpu._seh_just_redirected` flag right after any redirect; `_invoke_handler`'s loop responds by switching to much smaller batches (`_FINE_STEP_BATCH=50`, for `_FINE_STEP_WINDOW=3,000` steps) so the check actually catches the transition within a handful of instructions instead of missing it inside whatever's left of a normal 10,000-step batch.

**Two earlier detection ideas tried and live-disproven before this one** (see `status_archive.md` for full detail, kept here as the short version so this isn't re-derived): (1) "ESP >= the original exception's own SEH frame address" seemed principled but a full single-step trace proved ESP *never* got anywhere near that address during the real escape -- wrong assumption about where the real `__except` block resumes. (2) replicating `run_exe.py`'s outer-loop `preempt_slice`/timer-heartbeat servicing *inside* `_invoke_handler`'s loop (so a separately-discovered dedicated timer thread, `tid=1006`, could get CPU time) fixed nothing on its own, because the real problem was staying nested at all -- confirmed via `status_archive.md`'s existing "Timer thread: FUN_00a30ea0" note that the timer/thread subsystem already works correctly under normal (non-nested) execution, so neither the scheduler-to-Zig port nor the original SEH dispatch work ever broke it; this scenario (nested this deep, this long) simply never happened before tonight.

**Tests**: `test_dispatch_exception_returns_immediately_when_handler_resumes_far_from_itself` (renamed/rewritten from an ESP-based version once (1) above was disproven) in `tests/unit/kernel/test_seh.py` -- a synthetic handler whose RtlUnwind redirect lands 3MB away and spins forever (`jmp $`); asserts `dispatch_exception` returns `handled=True` quickly rather than exhausting `_STEP_LIMIT`. `pytest -q`: 1238/1238.

**Live-verified, the whole chain**: `CPU fault at EIP=0x004d980f -- attempting SEH dispatch` (6.197s) → `fault at 0x004d980f handled by game's own SEH chain -- resuming` (6.205s, **8ms**, not a 2-second-plus timeout) → execution continues normally for 42 more real seconds, reaching DirectX8 setup, DAO/DB thread startup (`stdout.txt`: `--DBThread is alive!`), and the game's own COM-licensing check (`dbcode.c(3376)`, known-ignorable per this file's "Known false leads") → **the real Motor City Online main window renders and stays up** → finally halts on a genuine, unrelated, downstream assertion: `ASSERT: mcity.c(588) prefClass>=0 && prefClass<DBCP_MaxRatings`, reported honestly via `INT3 breakpoint ... unhandled by SEH chain -- halting` at 48.481s, with a real 9-frame EBP chain all the way from the entry point (frame[8], `ret=0x00000000`) through `mainCRTStartup`'s own sentinel (frame[7], `ret=0x001ff000`) down to the assertion site. This is the furthest the emulator has ever run MCity_d.exe -- a new, real, separate investigation for next time, not a recurrence of anything from tonight.

**Also fixed, unrelated but discovered while live-testing tonight**: `run_exe.py` never installed a `SIGTERM`/`SIGINT` handler, so every `timeout N ... run_exe.py` invocation that actually hit its time limit (the standard way this project bounds a debugging run) got killed before `crt_state.window_manager.shutdown()` (→ `SDL_Quit()`) ever ran -- orphaning the SDL window/GL context every time, all night, which is almost certainly what was destabilizing KWin. Added a handler mirroring the normal post-run path (SDL shutdown, flush stdout, `os._exit()` -- not `sys.exit()`, same NVIDIA-driver-atexit-crash reason already documented at that call site) for both signals. Live-verified: a run force-killed via a short `timeout` now logs `Received signal 15 -- shutting down SDL2 before exit` followed by a clean `SDL2 shut down`, instead of just dying.

**Also found earlier tonight, unrelated, not yet fixed**: `_fputs`/`_fprintf` calls in `_WinMain@16` (`0x68a6ec`/`0x68a700`/`0x68a6d1`, real statically-linked CRT code, not a Python handler -- `msvcrt_handlers.py` having no `fputs` entry is a red herring) write through `(FILE*)&DAT_012804d0`, the CRT's static `stdout` slot -- `CreateFile("stdout.txt")` succeeds (confirmed live, handle `0x5004`) but that handle is never touched by any `WriteFile` call; the handle goes orphaned. Real MSVC CRT likely relies on `fopen`'s internal `_iob[]` slot-reuse (the just-`fclose`'d stdout slot getting handed back) to make `local_10 == &DAT_012804d0` without an explicit copy -- not yet confirmed whether tew's own file-handle/`_iob[]` modeling does this correctly. Low priority: `Channel_SystemPrint`'s separate `guest_stdout_handle` path already gets real output into `stdout.txt` (confirmed working), so this only affects the small number of *raw* `fputs`/`fprintf` calls in `WinMain` itself, not general game diagnostic output.
