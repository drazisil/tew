## Current status (2026-08-28, cont'd x37) — DB init now runs for real; new blocker is a genuine DAO/Jet query-parameter gap in `expsrv.dll`, not a missing Win32 handler.

**Five handler/bug fixes tonight, each verified by a fresh full re-run before moving to the next blocker**:

1. **`kernel32.dll!LoadLibraryA` full-path calls to our own Python-simulated-only DLLs never resolved** (`kernel32_handlers.py::_load_dll_by_path`) -- `stubs.get_stub_dll_handle(basename)` was only ever checked as a fallback *inside* `if real_path is not None:` (i.e. only when a real file was found on disk but failed to parse as a PE), never when `find_file_ci` legitimately found no real file at all. Hit at ~60s: real `OLEAUT32.dll`'s own NLS-cache-version helper (`FUN_7713c8d9`, decompiled in Ghidra to confirm -- see below) calls `LoadLibraryA("<cached SYSTEM32 dir>\kernel32.dll")` defensively before looking up `NlsGetCacheUpdateCount`; `kernel32.dll` has no real file backing it (Python-simulated only), so this fell through to the interactive-missing-file prompt and crashed into an unregistered trampoline slot on non-interactive stdin. Fixed by checking the stub-handle fallback in the not-found path too.
   - Root-caused via Ghidra: dumped `OLEAUT32.dll`'s own image base (`0x77120000` from its PE header) vs. its runtime load base (`0x10000000`) to translate the call's return address (`0x1001c957`) to a static Ghidra address (`0x7713c957`), ran `analyze_existing_program` (auto-analysis had never run on this program instance), and decompiled the caller directly -- confirmed it builds the path from its own zero-initialized `.data` global (populated earlier by a real `GetSystemDirectoryA` our own handler answered) plus a literal `"KERNEL32.dll"` string constant found via `search_strings`. Nothing host-specific (`.emu32`, etc.) is ever visible to the guest -- ruled out by design (`translate_windows_path` is host-side only) and confirmed by decompiling the actual mechanism, not just the symptom.
2. **Real bug found while fixing #1**: `os.path.basename()` is POSIX-only and silently doesn't split on `\` -- on Linux, `os.path.basename("C:\\WINDOWS\\SYSTEM32\\kernel32.dll")` returns the whole string unchanged, not `"kernel32.dll"`. Both `_load_dll_by_path` basename extractions (the pre-existing one and the new one from fix #1) now use `ntpath.basename()` instead, which has correct Windows path semantics regardless of host OS.
3. **`advapi32.dll!RegNotifyChangeKeyValue` unimplemented** -- since `registry.json` is only ever written by the guest process itself (no external registry mutation is modeled), a watched key never changes out from under it in our environment. Implemented as: synchronous mode (`hEvent==0`) returns success immediately (we can't actually block a thread forever); asynchronous mode (`hEvent!=0`) registers the watch and returns success without ever signaling `hEvent`, matching real Windows' own return-value semantics (success means "watch registered," not "already changed").
4. **`kernel32.dll!WaitForMultipleObjects` was a bare `_halt` stub despite `WaitForMultipleObjectsEx` right next to it having a complete, correct implementation** -- same 4 leading args at the same stack offsets, `Ex` just also reads an unused 5th `bAlertable` arg. Factored the shared logic into `_wait_for_multiple_common(cpu, arg_bytes)` and wired both entry points to it (16-byte vs 20-byte stdcall cleanup).
   - `bAlertable`/`SleepEx`'s alertable semantics are a real no-op right now: verified `QueueUserAPC`/`ReadFileEx`/`WriteFileEx` (the only three APIs that can ever queue an APC) aren't implemented anywhere, so there's no pending-APC state to interrupt a wait early. Harmless today; noted in `TODO.md` so it isn't forgotten if those three ever get implemented.
5. **`kernel32.dll!GetStringTypeExW` and `msvcrt.dll!wcsncmp` unimplemented** -- both straightforward siblings of already-implemented functions (`GetStringTypeW` plus a leading, classification-irrelevant `Locale` param; `strncmp`'s wide-char counterpart, same pattern as the existing `wcsncpy`/`strncpy` pair).

**Post-PR review follow-up (same session)**: an independent review of PR #5 (`gh pr create` https://github.com/drazisil/tew/pull/5) found two real issues, both fixed and pushed to the same branch:
- `RegNotifyChangeKeyValue`'s synchronous form was fabricating immediate success instead of really blocking -- fixed to route through the same handle-block scheduler machinery `WaitForSingleObject` uses (parked on a permanently-unsignaled sentinel event, since nothing external ever writes `registry.json`). Verified no hang/regression.
- `_lseek`/`_llseek` clamped position against `len(entry.data)`, which is always 0 for fd-backed (writable+readable) handles -- silently reset any nonzero seek to position 0. Added `file_entry_size()` (`_state.py`) using `os.fstat` for fd-backed handles. **Checked against the current `StockAssembly_SelectAPT` blocker below and confirmed NOT the cause** (identical halt, same EIP, before and after) -- but a real, independently-worth-fixing bug since DAO/Jet opens `.MDB` files exactly this way.

**Run now reaches ~80.5s** (vs ~60s at the start of tonight's session) and hits a **new, different class of blocker**: a real, unhandled `INT3` inside `MCity_d.exe` itself (not a missing-handler halt). `stdout.txt`'s own stated reason: `nfspc.c(1164) NFS_abortmsg callback 'AMF=166 DBQuery.c(997) DB ERROR: query StockAssembly_SelectAPT; could not get param count; does table really exist?'`.
